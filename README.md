# Lucid AI

Lucid AI is one of the eight main teams of the [Octacity](https://github.com/0ctacity) open-source community. The team works on artificial intelligence and the software built around it.

The team's interest is broad. Machine learning and deep learning are at the centre of it, but so is the data work that comes before a model and the engineering that comes after one. A project does not need to train a model to belong here — applications, libraries, datasets, tooling, and documentation are equally part of the team's work.

What the team cares about is that the work is understandable. A model whose behaviour cannot be explained, a result that cannot be reproduced, or a project that only its author can run is not finished work. Lucid AI would rather maintain a small system that others can read, run, and build on than a larger one that no one else can.

## Areas of Work

* **Machine learning** — prediction, classification, and analysis on structured and unstructured data
* **Deep learning** — neural network models and their practical application
* **Language and text** — language models, retrieval systems, and natural language processing, including work on Turkish
* **Computer vision** — image analysis, restoration, and detection
* **Autonomous and embedded systems** — perception, navigation, and models running on constrained hardware
* **Data engineering** — data collection, cleaning, pipelines, and storage
* **Infrastructure and tooling** — training, evaluation, deployment, and experiment tracking
* **Applications** — usable software built on top of models, including interfaces and dashboards
* **Datasets and benchmarks** — openly published data and evaluation resources
* **Learning resources** — reference implementations, reproductions, guides, and documentation

These describe where the team currently expects to work, not a limit on what it may work on. Proposals outside this list are welcome if they fit the community's goals.

## How the Team Works

Projects are proposed, discussed, and maintained openly. Anyone in the team may propose a project; anyone may contribute to one.

Projects start small. A narrow project that works and is maintained is more useful than a broad one that stalls. Scope can grow once something exists.

Work is documented as it happens, in issues, pull requests, and repository documentation, so that others can follow the reasoning and join later.

Results are reported honestly, with enough context to be understood — how they were measured, and what their limitations are.

Projects should be runnable by someone else: clear instructions, stated dependencies, and a documented data source.

## Current Status

The team is newly formed. Its first projects are still being discussed, and its structure will develop as that work begins.

This is a good time to join. Early members will help decide what the team builds first and how it organizes itself, rather than joining work that is already defined.

People interested in the team should follow this repository and its discussions. Information about membership is available in the [membership repository](https://github.com/0ctacity/membership).

## Contributing

Contribution is not limited to writing models. Depending on the project, useful work includes software development, data collection and cleaning, model development and evaluation, infrastructure and deployment, interface and visualization work, testing, documentation and technical writing, research and reproduction, code review, and helping new contributors.

Contributors without prior experience in machine learning can start with documentation, data work, testing, or reproducing existing results.

Contribution guidelines, the code of conduct, and other community standards are maintained in the [Octacity community files repository](https://github.com/0ctacity/.github). Individual repositories may define additional requirements, and each states its own contribution policy.

## Communication

Technical discussion and planning take place through GitHub issues, pull requests, and discussions in the relevant repository. Decisions that affect a project's direction are recorded there rather than left in private conversations.

Disagreement about technical approaches is expected and welcome, as long as it stays focused on the work.
